# EPF Week 8 - Ivan Anishchuk - Heze merged and the Merkle completeness stack in five PRs

Short version:

- Heze PR is merged. The FOCIL fork layer is on main and conformance is green at both
  presets.
- The Merkle-proof completeness result is up as a five-PR stack.
- Everything in the stack rebuilt and retested, all green.

## Heze landed

The Heze fork layer, EIP-7805 FOCIL included, is merged and conformance-complete at both
presets. Third fork etheorem models, after Fulu and Gloas.

It took a while to review and merge, mainly because we kept finding pre-existing issues
along the way: minor spec-faithfulness things, mostly, like our model not throwing where
the python spec does. I split the fixes off into a separate PR to keep the main one from
exploding. Either way, it's all on main now.

## Merkle proof completeness

The theorem says `is_valid_merkle_branch` accepts every honest opening of a tree the
implementation builds. Open the tree at an index, hand the check that leaf and the
sibling path, and you get `true` back.

I had the main theorem proven for a while, but after the Heze PR explosion I split it into a
stack of five pull requests, bottom to top:

| PR | What it adds |
| --- | --- |
| [#71](https://github.com/etheorem/etheorem/pull/71) | `compute_merkle_branch_root`, and a guard rejecting a branch whose length disagrees with the claimed depth |
| [#72](https://github.com/etheorem/etheorem/pull/72) | The tree-shape vocabulary the later statements quantify over |
| [#42](https://github.com/etheorem/etheorem/pull/42) | The completeness theorem, over any tree the implementation can open |
| [#66](https://github.com/etheorem/etheorem/pull/66) | `get_generalized_index` over the SSZ types, and completeness at the indices it returns for container paths |
| [#67](https://github.com/etheorem/etheorem/pull/67) | Agreement between the cached tree root and `hash_tree_root` |

The first one models a helper we didn't have and makes the length guard spec-faithful: a
branch whose length disagrees with the claimed depth is now rejected outright, the way
pyspec does, instead of folding in defaults. The other four are the proofs, split
granularly: lemmas and preliminaries, the completeness theorem itself, gindex
applications, and hash-tree-root agreement.

The gindex bits and the htr/merkleizer agreement are important on their own, and they pave the
road for other Merkle-related parts of the protocol, light client sync in particular.
The latter needs modeling work first though. Those two PRs are currently a
little bit on the bigger side, it's possible that I'll split them further,
especially if any more additions are needed.

## Where it's used

Clients run this check in a few places, deposits against the deposit contract root, light
client finality and sync committee updates against the beacon state root, PeerDAS column
sidecars against the block body root.

What completeness buys is that an honest proof never gets rejected.
Sounds trivial but getting that right means the index arithmetic, the zero-padding on a partial layer and the
SSZ type's own chunk count all have to agree, which is (I think) where implementations
might silently drift apart.

## What it doesn't cover

Completeness says the verifier accepts honest proofs. It says nothing about soundness,
rejecting forged ones. I'm still exploring that direction; it should be provable, modulo
a collision-resistance assumption.

Completeness stated at the reference Sha256 hasher carries one named axiom, that
the FFI SHA-256 agrees with the pure-Lean implementation. At the native
Lean hasher the same results are axiom-free.

## Validation

Every branch tip was rebuilt and retested from the bottom up, so each PR can go in on its
own. Theorems machine-checked, model checked against the vector tests.

## In flight

Right now the verified leaf is stated as a chunk. If we restate it as the field's own
`hash_tree_root`, a caller can match the theorem straight against a sidecar inclusion
proof, no intermediate step. Light client sync proofs need spec modeling and a few other
preliminaries before that though.

Next up, once the Merkle stack is finalized: overflow safety and the slot/epoch
invariants.
