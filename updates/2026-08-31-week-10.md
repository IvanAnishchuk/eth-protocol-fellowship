# EPF Week 10 - Ivan Anishchuk - balance mutators and throw-faithful arithmetic

Short version:

- Balance mutators proved not to wrap ([#80](https://github.com/etheorem/etheorem/pull/80), merged).
- Eight PRs of arithmetic and structural invariants: slot/epoch conversions,
  the activation-exit epoch, churn, deposits, builder balances, committee size.
- Five of them make seven spec functions reject on overflow the way pyspec does, where our
  model used to wrap.
- The verification roadmap ([#35](https://github.com/etheorem/etheorem/pull/35)) and an
  axiom allow-list fix ([#79](https://github.com/etheorem/etheorem/pull/79)) are merged.

## Balance mutators

[#80](https://github.com/etheorem/etheorem/pull/80) proves seven theorems about
`increaseBalance` and `decreaseBalance` in Fulu: an exact run equation and an out-of-range
reject for each, the overflow reject and exact stored sum for the increase, the truncating
difference for the decrease.

Most of the work was changing the model. Neither mutator could reject at all, so both had
to become `StateTransition` actions first. `balances` is now read through `sszGetIdx`, so an
index past the end rejects (pyspec raises `IndexError`). The addition goes through
`checkedAdd`, so overflow rejects (`ValueError` upstream). Gloas and Heze inherit both
without an edit. It's also the first step in converting the rest of the state-transition
`uint64` arithmetic ([#44](https://github.com/etheorem/etheorem/issues/44)).

Whether a reject counts as faithful depends on what the reference test's own wrapper
catches. I added a `RunnerCaughtSet` that maps a runner/handler pair to that set, and
`classifyReject`, which turns a reject plus a set into a case result (this closed
[#41](https://github.com/etheorem/etheorem/issues/41)).
That's the part I'd most like reviewed.

## Throw-faithful

Each PR does the same thing. The pyspec does its arithmetic on `uint64`, and remerkleable raises
`ValueError` past `2^64 - 1` (or `ZeroDivisionError` on a zero divisor). Our Lean body
wrapped instead. Each PR switches it to the checked operator, rejects with `.arithmetic`,
and proves where that reject can and can't fire.

| PR | Spec functions |
| --- | --- |
| [#103](https://github.com/etheorem/etheorem/pull/103) | `compute_start_slot_at_epoch` (the multiply) |
| [#104](https://github.com/etheorem/etheorem/pull/104) | `compute_activation_exit_epoch` (`epoch + 1 + MAX_SEED_LOOKAHEAD`) |
| [#105](https://github.com/etheorem/etheorem/pull/105) | `compute_exit_epoch_and_update_churn` and `compute_consolidation_epoch_and_update_churn`, through the shared churn reservation (zero limit, epoch add, multiply, consumed add) |
| [#106](https://github.com/etheorem/etheorem/pull/106) | `process_deposit`'s `eth1_deposit_index += 1` |
| [#110](https://github.com/etheorem/etheorem/pull/110) | Gloas `get_pending_balance_to_withdraw_for_builder` and `can_builder_cover_bid` |

The more useful theorems say where the reject can't fire. An epoch that came out of
`compute_epoch_at_slot` never overflows `compute_start_slot_at_epoch`, with no extra
hypothesis, and never overflows `compute_activation_exit_epoch` under a preset bound both
shipped presets satisfy. A successful churn reservation returns a consumed total at least as
large as the balance, so the callers' subtraction never underflows. `process_operations`
only runs a deposit while the index is below `deposit_count`, itself a `uint64`, so the
increment can't overflow there. [#103](https://github.com/etheorem/etheorem/pull/103)
also proves the slot/epoch round trip and monotonicity at Fulu, Gloas and Heze.

The Gloas consolidation churn limit has no `MIN` floor, so it can be zero. The old
model divided by it and got `0`.

## Invariants

- [#107](https://github.com/etheorem/etheorem/pull/107): the deposit path keeps
  `validators` and `balances` the same length. That equality is also why our
  `addValidatorToRegistry` (push onto every list) agrees with the spec's
  `set_or_append_list` at `index = len(state.validators)`.
- [#108](https://github.com/etheorem/etheorem/pull/108): Gloas `apply_withdrawals` keeps the
  builder registry's size, and no builder balance ends above where it started, over any
  withdrawals array. Proofs only. The body already matched the spec.
- [#109](https://github.com/etheorem/etheorem/pull/109): committee size bound. At mainnet an
  active count in `[32, 2^22]` puts every committee in `(0, 2048]`, the same bound the Dafny
  work proves as `ActiveValidatorBounds`. At minimal the range is `[8, 65536]`.

Lean checks the theorems, and the changed spec functions pass the pyspec vectors.

## Roadmap merged

[#35](https://github.com/etheorem/etheorem/pull/35) is in. It went in as rows in etheorem's
proof ledger instead of a separate roadmap document, and I think that works better. The
coverage baseline records what's proved, and the ledger records what we mean to prove, one
row per candidate function with its property, status, and the PR tracking it.

The rows also can't go stale unnoticed. Each cites the lines of the fork body it's about,
and CI fails when a citation no longer matches the declaration its row names.

## Axiom allow-list

CI collects the axioms each proof claim rests on and fails on any outside the allow-list.
The trust-footprint line in each PR description comes from this check, so readers don't
have to take my word for which axioms a proof uses.

The list named the two SHA-256 FFI-equals-spec axioms under the wrong namespace, so those
entries matched nothing. [#79](https://github.com/etheorem/etheorem/pull/79) fixes that.
The merkleization proofs use those axioms, so the fix had to land first.

Leo also posted SizzLean, the SSZ library under etheorem, on ethresear.ch:
[Lean4 SSZ library: formally verified and easy to use](https://ethresear.ch/t/lean4-ssz-library-formally-verified-and-easy-to-use/25988).
It covers the codec proofs and merkleization, and names three SHA-256 FFI-equals-spec
axioms as the whole trust base.
