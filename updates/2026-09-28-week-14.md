# EPF Week 14 - Ivan Anishchuk - what FOCIL and ePBS guarantee together

Short version:

- New direction: what FOCIL and ePBS guarantee together, proved on the Heze fork body
  (consensus-specs `v1.7.0-alpha.11`).
- Three stacked PRs are up for review: [#113](https://github.com/etheorem/etheorem/pull/113) →
  [#114](https://github.com/etheorem/etheorem/pull/114) →
  [#115](https://github.com/etheorem/etheorem/pull/115). All build, no `sorry`, no axioms in
  the proofs (the test witness uses `native_decide`).
- The last one proves a preliminary inclusion dichotomy for one node and one block, with
  every assumption stated as a hypothesis, and a test witness that meets them all at once.

## The question

FOCIL (EIP-7805) and ePBS (EIP-7732) each constrain builders on their own. In the pinned
spec, Heze adds FOCIL on top of Gloas's ePBS, so the question is what the pair
guarantees together. The claim I'm after is that a builder can only drop an honest inclusion-list
transaction by giving up its payload for that slot, and that it still pays its bid if the
beacon block reached the attestation quorum.

That's the intended design, not a new idea. Zanolini and Saltini's
[integration of 3SF with ePBS, FOCIL and PeerDAS](https://ethresear.ch/t/integrating-3sf-with-epbs-focil-and-peerdas/22909)
gives the same fork-choice rule and notes that its properties haven't been proven formally.
The closest formal work is Rahul Barman's
[Formalizing FOCIL in Lean 4](https://ethresear.ch/t/formalizing-focil-in-lean-4/24950),
which proves the network-level inclusion claim on an abstract FOCIL model. Mine works on the
executable spec functions and includes ePBS, but covers one node only.

A payload that fails the inclusion list stays valid. Fork choice just declines to extend it,
so the whole FOCIL effect goes through one tiebreak between the FULL and EMPTY nodes.

## What the PRs prove

[#113](https://github.com/etheorem/etheorem/pull/113) covers what a failed inclusion list
costs. At a previous-slot block with a verified payload and a recorded `false` answer, one
step of `get_head` picks EMPTY. Both weights are zero there, so the tiebreak decides. A
child block on the EMPTY edge doesn't settle the parent's bid, because
`process_parent_execution_payload` returns the state unchanged on that edge. The PR also
ports the Gloas builder-payment proof to Heze and adds two facts about the epoch substep.
An entry qualifies if and only if its weight reaches the quorum, and a bid whose entry is
carried to the epoch boundary is paid if and only if that entry reached the quorum
("carried" means no proposer slashing and no child on the FULL edge in between). The
`get_head` fact and the child fact stay separate. The link between them, a proposer building
on the head, isn't modeled, so it's an honest-behavior assumption.

[#114](https://github.com/etheorem/etheorem/pull/114) proves six laws for the fork-choice
maps (`LawfulFcMap`), for both map types the model uses. The tree map also needs order laws,
which come from showing that `Root`'s byte-loop `compare` equals core's lexicographic order.
With those, the envelope handler provably stores the payload and the EL's inclusion-list
answer at the same root.

[#115](https://github.com/etheorem/etheorem/pull/115) proves the dichotomy. Take a block
and one transaction from an honest inclusion list for the slot before it. The envelope
handler succeeds, and then one of two things holds. Either the EL answers `true` and the
transaction is in the payload or validly omitted, or it answers `false` and the facts from
[#113](https://github.com/etheorem/etheorem/pull/113) hold in the slot after the block. The
second case needs the store to still have the block and the answer at that root.

A corollary covers the transaction itself: if it's missing and not validly omitted, the
answer must be `false`, and with the facts above that gives the cost. The PR also restates
the `get_head` step over the whole loop and drops the verified-payload premise, since an
unverified payload goes to EMPTY too. A withheld payload is a separate lemma: before the
envelope, the pending node has only the EMPTY child.

A test witness builds a minimal-preset store, a self-build envelope and an honest
list that meet every hypothesis at once, and on it the `false` branch fires for a real
missing transaction.

## What it assumes

The dichotomy holds under these hypotheses, and several of them are about things outside
fork choice:

- the EL applies the inclusion rule from the
  [FOCIL CL and EL workflow](https://ethresear.ch/t/focil-cl-el-workflow/20526)
  (`LawfulInclusionList`, a hypothesis the theorems take;
  with an always-true omission predicate the `true` case says nothing)
- one list per validator per committee key (`on_inclusion_list` checks no signature; gossip
  does)
- no later list collides with the honest list's root (lists are keyed by `hash_tree_root`)
- the honest list's first arrival is timely (a later copy doesn't update timeliness)
- the honest list carries the committee the block's state computes
- the IL store is the fold of the arrivals, so no other handler writes it
- the envelope handler and the committee lookup succeed
- in the next slot the store still has the block and the answer at that root (`LaterStore`)

A `false` answer is about the whole collected list, so it can come from another list's
transaction.
